# 成本护栏需求文档（每个账号的 AI 额度）

| | |
| --- | --- |
| 状态 | **已实现并验证**（见 [STATUS.md](STATUS.md) 2026-10-16） |
| 目标 | 把"模型调用"当成共享成本管起来：每人每天有上限、同时有并发上限、顶栏看得见剩余 |
| 关联 | [MISTAKE-BOOK-REQUIREMENTS.md](MISTAKE-BOOK-REQUIREMENTS.md)、[DEPLOYMENT.md](DEPLOYMENT.md)、[USER-GUIDE.md](USER-GUIDE.md) |

---

## 1. 为什么要做

系统里所有花钱的动作（出题、追问、转写、评分、简答判分、简历优化、语音合成）过去**没有任何计量**：

- 一个账号写个脚本连点"生成题目"，就能把当天所有额度烧光 —— 而这是所有用户共享的成本；
- 已有的限流只管登录（防爆破），**完全挡不住这个**；
- 用户也不知道自己在花什么、还剩多少，被拦住时只会觉得"网站坏了"。

一句话：**能开放给别人用之前，先让成本有上限、让用户看得见。**

---

## 2. 范围

### 2.1 本期做

1. **每个账号每日调用上限**（默认 120 次）与**并发上限**（默认 3 个在飞请求）；
2. 计数放 **Redis**（多实例共享、重启不丢）；Redis 不可用时**退到进程内存**并记一条警告；
3. **同步入口拿不到额度 → 429 + 一句人话**（"今天的 AI 额度已经用完了（每天 120 次，明天 0 点重置）"）；
4. **异步分析链路拿不到额度 → 顺延，不失败**：把任务推迟到额度重置之后重跑，不消耗重试次数、不进死信队列；
5. `GET /api/v1/me/model-usage` 返回剩余额度，前端顶栏常显"今日 AI 额度 x/y"；
6. 追问这类"少一次也不影响练习"的调用，额度用完时**降级为不追问**，不弹错。

### 2.2 刻意不做

| 决定 | 原因 |
| --- | --- |
| 不做按 token 计费 | 那需要解析每家的用量回执，先做"按次"就已经能挡住跑飞 |
| 不做充值/付费 | 这是给自部署与内部使用搭的护栏，不是计费系统 |
| 不按"模型请求"精确计数笔试出题 | 一次"笔试出题"内部可能自检重试若干轮，这里按**用户可感知的一次操作**计 1 —— 挡的是"能开多少场"，不是账单分毫不差（见限制 1） |
| 不做管理端改额度 | 用配置项（`quota.model.*`）即可，先不做后台 |

## 3. 功能需求（FR-11）

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| FR-11.1 | 每日上限 | 按"账号 + 自然日（默认 Asia/Shanghai）"计数；键带 TTL 到次日 0 点 + 60 秒 |
| FR-11.2 | 并发上限 | 同一账号在飞的模型调用超过上限即拒绝；在飞计数带兜底 TTL（10 分钟），进程被 kill 不会把账号永久锁死 |
| FR-11.3 | 扣减语义 | **先占名额再调用**；调用失败也扣（失败往往同样消耗 token）；被拒的那一次要还回去，否则"剩余额度"会一直往前飘 |
| FR-11.4 | 拒绝要清楚 | 429 + 统一错误体 `{code, message}`，消息里写清上限与恢复时间；不是 500，也不是静默失败 |
| FR-11.5 | 异步顺延 | 分析任务的转写/评分拿到"额度不足"时：任务回到 `pending`、`nextAttemptAt` 设为额度重置后（错开 0-120 秒），**不计失败次数**；第二天报告正常生成 |
| FR-11.6 | 降级而非报错 | 追问在额度用完时返回"这次不追问 + 原因"，练习照常进入下一题 |
| FR-11.7 | 前端可见 | 顶栏显示"今日 AI 额度 剩余/上限 + 重置时间"；剩 10% 变琥珀色，用完变红；拿不到就不显示（不打扰） |
| FR-11.8 | 计数哪些调用 | 面试出题、笔试出题、简答判分、追问（转写 + 判断）、内容评分与转写、简历生成/补全/优化、语音合成（含示范回答播报）；**本地沙箱判题、上传、报告查询不计** |
| FR-11.9 | 可关掉 | `quota.model.enabled=false` 完全不拦（本地压测/开发用） |
| FR-11.10 | 隔离与归属 | 额度按 token 里的账号计；未登录 401 |

## 4. 实现位置

| 位置 | 作用 |
| --- | --- |
| `consumer/.../quota/ModelCallGuard` | 计数与判定（`call` / `tryAcquire` / `require` / `usage`）；Redis 与内存两种计数实现都在这个类里 |
| `consumer/.../quota/ModelUsageController` | `GET /api/v1/me/model-usage` |
| `consumer/.../analysis/AnalysisJobService` | 异步顺延（`AnalysisDeferredException`） |
| 各入口 | 出题 / 追问 / 判分 / 简历 / 语音合成 的 `guard.call(...)` 包裹（见 FR-11.8） |
| `web/src/services/modelUsage.js` + `App.vue` | 顶栏额度条与文案（纯计算可单测） |

配置（`application.properties`，都能用环境变量覆盖）：

```properties
quota.model.enabled=${QUOTA_MODEL_ENABLED:true}
quota.model.daily-limit=${QUOTA_MODEL_DAILY_LIMIT:120}
quota.model.max-concurrent=${QUOTA_MODEL_MAX_CONCURRENT:3}
quota.model.zone=${QUOTA_MODEL_ZONE:Asia/Shanghai}
```

## 5. 验收标准

| # | 验收项 | 通过判据 |
| --- | --- | --- |
| A25 | 上限真的挡住 | 把上限压到 2：前两次真模型出题成功，第三次 **429** 且消息含"额度"（`scripts/verify-quota-limit.ps1`） |
| A26 | 计数在 Redis | 额度键出现在 Redis 里；重启后当天已用次数不清零（同上脚本） |
| A27 | 其它入口同样挡 | 额度用完时 `GET .../narration/audio` 也是 429（不是 500） |
| A28 | 前端可见 | 顶栏显示"今日 AI 额度 118/120 · 00:00 重置"（浏览器实测） |
| A29 | 不误伤 | 本地沙箱判题、上传、读报告不计入；关掉护栏时一切照常（单测覆盖） |

## 6. 已知限制

1. **一次"笔试出题"记 1 次**，即使内部自检重试了 3 轮。要精确到每次模型请求，得把账号透传到
   `CodingQuestionPlanService` 里逐次计数 —— 现在有意留着这个近似，换实现上的简单。
2. **内存兜底是退化方案**：Redis 不可用时多实例各算各的、重启清零。它是"别让应用不可用"的兜底，
   不是等价方案（日志里会留一条警告）。
3. **额度按自然日重置**，不是滚动 24 小时窗口；跨时区部署要显式改 `quota.model.zone`。
4. 额度用完时，**正在排队的分析任务会顺延到第二天**：用户看到的是"等待分析"变久，而不是报告失败。
   如果这不可接受，应当在 API 层就给用户明确提示（现在是靠额度条提前告知）。

## 7. 需要你决定的问题

| # | 问题 | 我的建议 |
| --- | --- | --- |
| Q18 | 120 次/天合适吗？ | 一轮 5 题练习大约 15-20 次（出题 1 + 追问 3 + 转写/评分 10-12 + 配音 5），够练 5-6 场；先这样，有真实用户再按分布调 |
| Q19 | 并发 3 个够吗？ | 单个用户正常不会并发，3 是防"脚本连点"的护栏；要压测时用 `quota.model.enabled=false` |
| Q20 | 要不要给新注册账号更小的额度？ | 可以先一样。真要防滥用，应该先做"每账号每日会话数"而不是只调这个数 |
